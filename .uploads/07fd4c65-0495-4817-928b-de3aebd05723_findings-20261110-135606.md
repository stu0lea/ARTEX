### 1. [CRITICAL] filemover.sd2000.com:24006 文件接口全面未授权（匿名任意目录列举 + 任意本地文件复制 + 宿主路径删除/写入）

filemover.sd2000.com:24006（后端 piscenter-filemover:20006）的全部 WebFiles/WebOrderFiles 接口对匿名用户完全开放且不校验任何路径归属：匿名可列举服务器任意目录（C:/、C:\Windows\System32\inetsrv 工作目录、C:\Windows\Temp 29801 项、Windows 系统目录，并可用 UNC \\127.0.0.1\c$\Windows 绕过），可匿名调用 CopyAIRetouchingFiles 把任意服务器本地文件复制成可读记录（以 C:/Windows/win.ini 为例返回 /upload/yunxiu/20261031/I40ANONwin.ini），还可匿名调用 Remove/BatchRemove/RenameFolder/Upload/Upload3D/BatchCreateOrderFileMerge 等写/删类接口，且操作对象为宿主 Windows 文件系统绝对路径；任务提供的登录 cookie 与匿名响应逐字节相同，说明认证与租户隔离在服务端完全缺失。

## 概述

`https://filemover.sd2000.com:24006`（前端 tengine，回源内网 ASP.NET 应用 `piscenter-filemover:20006`）的 `WebFiles` / `WebOrderFiles` 文件接口组**完全没有认证与授权校验**：匿名攻击者无需任何 Cookie 即可列举服务器的任意绝对路径目录（含 UNC 与设备前缀）、把任意可读本地文件复制到图片库命名空间、并调用删除 / 批量删除 / 重命名 / 上传 / 合并等写操作接口，且这些接口操作的对象是**宿主机 Windows 文件系统的真实路径**。任务提供的已登录 Cookie 与匿名请求在上述接口上响应完全一致，说明认证与多租户隔离在服务端整体缺失。

## 影响与危害

**严重等级：Critical**

| 维度 | 结论 |
|---|---|
| 认证要求 | 无（匿名可调用全部 10 个存活接口） |
| 权限边界 | 无（Cookie 与匿名无任何差异，`CustomerId` / `orderSN` 归属校验不存在） |
| 已验证能力 | 任意目录枚举、文件存在性判定、任意可读文件复制、删除/重命名/上传接口匿名可达 |
| 未完全验证 | 复制出的文件内容能否被回读（24006 上取回为 tengine 404）、任意文件写入后的代码执行 |

具体危害：

1. **主机与内网信息全面暴露**：匿名可枚举 `C:\`、`C:\Windows`、`C:\Windows\System32`、`C:\Windows\System32\inetsrv`（进程工作目录）、`C:\Windows\Temp`（一次返回 29801 条）、`C:\inetpub\wwwroot`、`C:\ProgramData` 等目录的文件名与扩展名；配合 `pathEncrypt=.` 可确定 Web 进程的工作目录，为后续选点（配置文件、日志、备份、运维脚本）提供直接依据。
2. **任意文件存在性预言机（可被大规模滥用）**：`CopyAIRetouchingFiles` 对存在的源文件返回 `Success:true` 并给出目标相对路径，对不存在的源文件返回 `500 文件X不存在`，对无权限路径返回“访问被拒绝”。三者可区分，等价于一个无需认证的 `File.Exists` + 可读性探测服务。
3. **敏感文件外带风险**：已验证可匿名把 `C:/Windows/win.ini`、`C:/inetpub/wwwroot/iisstart.png` 复制进 `/upload/yunxiu/<date>/` 命名空间。该存储根由同组织其它主机静态托管（同任务的关联漏洞 finding #10 已验证 `https://files.sd2000.com:9600/pisweb` 可匿名取回上传文件），因此“复制成功 → 公开可下载”的链路在本目标资产组内具备现实可行性（本报告中 `/upload/yunxiu/...` 的具体回读 URL 未验证）。
4. **破坏性操作接口匿名可达**：`Remove` / `BatchRemove` / `RenameFolder` / `BatchCreateOrderFileMerge` / `Upload` / `Upload3D` 全部匿名可用，且直接作用于宿主绝对路径。`Remove C:/Windows/win.ini` 返回 `NTFS 访问被拒绝`（证明它真的在执行删除而非仅回显），最终破坏上限仅取决于应用池账号的 NTFS 权限。关联漏洞 finding #9 已证实同一应用可匿名把任意内容写入 `C:/Windows/Temp`、`C:/Users/Public`、`C:/ProgramData` 等目录并落盘成功。
5. **多租户隔离彻底失效**：`Tag`、`OrderSN`、`sourceFilePath`、`pathEncrypt` 等参数均为客户端可控且直接进入路径拼接，未与 Token 中的 `CustomerId`（`b29fb9db-de6b-cb3d-a9d3-3a24a1c72d11`）做任何绑定，跨客户越权等价于“任意路径操作”。

综合判定为 **Critical**：无需凭据、可枚举宿主文件系统、可触发文件复制与写删操作，且已具备跨主机（files 静态站点）外带敏感文件的可行链条。

## PoC

以下脚本为**匿名利用**的完整可运行版本，覆盖“指纹确认 → 目录枚举 → 存在性探测 → 复制外带候选”，只用 `curl` 与 Python 标准库。

```bash
#!/usr/bin/env bash
# filemover_unauthed_poc.sh —— 未授权文件系统操作验证（仅用于授权测试）
# 用法: ./filemover_unauthed_poc.sh
set -u
BASE='https://filemover.sd2000.com:24006'
UA='Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/125.0 Safari/537.36'
# 注意：故意不带任何 Cookie

list_dir () {  # $1 = 目标路径（绝对/相对/UNC）
  curl -sk -G "$BASE/api/WebOrderFiles/GetFileInfosV2" \
```

## 根因分析

1. **控制器层面完全没有身份验证**：`WebFilesController` / `WebOrderFilesController` 未挂任何鉴权过滤器（无 `[Authorize]`、无 JWT/`ow` Token 校验、无网关鉴权），tengine 仅做反向代理与路由，转发到 `piscenter-filemover:20006` 后直接执行业务逻辑。因此 Cookie 对响应零影响。
2. **授权（对象级）缺失**：接口内不读取 Token 中的 `CustomerId` 做归属判断，`Tag` / `OrderSN` / `sourceFilePath` 全部取自请求体，跨租户访问等价于不存在。
3. **把“路径”当参数直接落地到文件 API**：`pathEncrypt` 的值（名称暗示加密，实际就是明文路径，见 fact 43）被直接交给 `Directory.GetFiles`；未做 `Path.GetFullPath` + 根目录前缀白名单校验，也未拒绝绝对路径、UNC（`\\127.0.0.1\c$`）、设备前缀（`\\.\C:`）与 `..`，因此可穿越到任意位置。
4. **上传/复制类接口用请求参数拼接存储路径**：`Tag`、`OrderSN`、`TempSerialSN`、`sourceFilePath` 直接参与路径拼接（拼接结果原样回显，如 `/upload/3D/20261031/..\..\Windows\Temp/x.png`），说明缺少规范化与边界校验（参见 finding #9 / #10）。
5. **错误信息过度回显**：直接向客户端返回 `文件C:/...不存在`、`对路径“C:\Windows\win.ini”的访问被拒绝`、以及 ASP.NET 404 中的内部地址 `http://piscenter-filemover:20006`，把服务端文件系统语义与内网拓扑暴露给匿名用户，并顺带形成高精度文件存在性预言机。
6. **默认拒绝策略缺位**：整个文件服务被当作“内网可信调用方”设计（由前端页面直接调用），没有对外暴露时的认证/限流/WAF 规则。

## 修复建议

**立即（P0，1~3 天内）**

1. **在网关与服务两侧同时加认证**：tengine 上对该 host 的 `/api/WebFiles/*`、`/api/WebOrderFiles/*` 强制校验登录态（转发校验 `sl-session`/`ow` JWT 签名，校验 `iss/aud/exp`），服务侧补充 `[Authorize]`/中间件；未认证请求统一返回 401，不能下探到业务逻辑。
2. **补齐对象级授权**：所有接口从 Token 取 `CustomerId`，与请求中的 `orderSN` / `Tag` / 文件路径做归属校验；无归属关系返回 403。禁止客户端指定任意 `sourceFilePath` 作为落盘目录。
3. **路径白名单化**：引入唯一的“存储根”配置（如 `C:\pisweb`），所有入参路径先 `Path.GetFullPath` 规范化，再校验 `fullPath.StartsWith(root, OrdinalIgnoreCase)`，否则拒绝；显式拒绝 UNC（`\\`、`//` 开头）、设备前缀（`\\.\`、`\\?\`）、驱动器绝对路径与 `..`。
4. **下线目录枚举能力**：`GetFileInfosV2` 不应接受客户端路径，改为按 `orderSN` + 服务端库表映射出目录；如确需回显文件名，只返回该订单目录下的条目并限制条数。
5. **收敛错误信息**：统一返回通用错误码，禁止回显服务器绝对路径、NTFS 错误与内部主机名；关闭 `X-AspNet-Version`、`X-Powered-By` 等指纹头。

**短期（P1，2 周内）**

6. 复核 `CopyAIRetouchingFiles` 的业务必要性：若只是“AI 修图取件”，源文件应限定在受管订单目录内并做归属校验，禁止任意绝对路径。
7. `Remove` / `BatchRemove` / `RenameFolder` / `BatchCreateOrderFileMerge` 增加软删除 + 操作审计（记录操作者、CustomerId、orderSN、原始/目标路径、IP），审计日志异地留存。
8. 上传类接口按 `finding #9 / #10` 一并整改：扩展名白名单之外再加内容魔数校验、文件名服务端生成、`TempSerialSN` 走 UUID 校验、禁止把拼接结果直接用作路径。

**长期（P2）**

9. 将文件服务改造为“以不透明 ID 换路径”的模型：客户端永远拿不到、也传不了真实路径；所有文件操作通过 order/file 主键 + 权限表完成。
10. 该服务置于独立安全域，仅允许网关访问（网络 ACL），关闭对外直连端口；对文件操作接口做速率限制与异常行为告警（短时间大量列目录 / 大量存在性探测即为典型攻击特征）。
11. 编制并回归一套自动化用例（匿名访问必须 401、跨 CustomerId 必须 403、`..`/UNC/绝对路径必须 400），纳入 CI。

---

## 概述

`https://filemover.sd2000.com:24006/api/WebOrderFiles/Upload` 是一个**无需任何 Cookie / Header 即可调用**的 multipart 上传接口。其业务参数 `sourceFilePath` 本应是"文件要保存到的目录"的提示值，服务端却把它**直接拼接成落盘绝对路径**（未做根目录约束、未做规范化后前缀校验），配合客户端可控的 `filename`，攻击者可在**服务器任意已存在目录**写入**任意文件名、任意内容**的文件，并能**自动创建子目录**。实测已在 `C:/Windows/Temp`、`C:/Users/Public`、`C:/ProgramData`、`C:/pisweb`、`C:/pisweb/upload`、`C:/pisweb/20261031` 成功落盘，并通过同主机 `GET /api/WebOrderFiles/GetFileInfosV2?pathEncrypt=<目录>` 列目录确认文件真实存在。

---

## 影响与危害

**结论：Critical。** 依据如下：

1. **零认证、零交互**：不带任何 Cookie（任务提供的 `sl-session`/`ow` 也不影响结果）即成功写入，`UnAuthorizedRequest:false`，接口对匿名完全开放；同主机全部接口的匿名与登录态响应逐字节一致（见关联事实 "cookie 对响应零影响"）。
2. **写入位置完全由攻击者决定**：路径不是"上传目录下拼接"，而是直接把 `sourceFilePath` 当绝对路径用，命中 `C:/Windows/Temp`、`C:/ProgramData`、`C:/Users/Public` 等系统可写目录，且 `C:/ProgramData/i37sub` 表明**可以凭写入自动创建不存在的子目录**。
3. **跨系统/跨租户的共享存储根被打穿**：`C:/pisweb` 是该业务的文件存储根（由 `https://files.sd2000.com:9600/pisweb` 静态托管，属生产文件服务）。本次可向其根目录及 `upload/` 子目录写入文件，构成对**全平台上传文件库的写入面**：可植入伪造的订单文件/图片/PDF，污染客户取件内容（覆盖既有文件的破坏性效果本次未做验证，见"局限"）。
4. **可组合放大**：(a) 已确认可写系统目录，若任一被写目录进入某进程的 DLL/插件/配置搜索路径，配合文件后缀限制的绕过即可升级为代码执行（本漏洞自身受扩展名白名单限制，尚未拿下 RCE，故不宣称已 RCE）；(b) 与同任务已确认的 `GetFileInfosV2` 任意目录列举（finding #7）组合，可形成"任意目录枚举 + 任意目录写入"的完整落地面；(c) 差异化错误回显（"对路径…的访问被拒绝" vs "上传的文件路径不合法"）构成**目录/路径存在性预言机**，可用于内网/主机结构探测。

**为什么不是 High 而是 Critical**：写入路径、文件名、内容三者均由未认证外部输入决定，且落点覆盖操作系统临时/公共目录与生产文件存储根，属于"任意文件写入"这一类可链式利用的高危原语；扣分项（未能直接落地可执行后缀、未拿到文件内容回读）已在"局限"中如实标注，不影响任意写的成立。

## 根因分析

1. **信任客户端给出的服务端路径**：`sourceFilePath` 语义上应是逻辑标识，实现上被直接作为落盘目录字符串使用（`FilePath` 回显为 `sourceFilePath + "\\" + filename`），整个链路没有"固定根目录 + 子路径"的约束。
2. **缺少规范化后前缀校验**：正确做法是先 `Path.GetFullPath()` 归一化，再校验结果以 `C:\pisweb\upload\` 之类固定根开头；当前既未归一化也未校验，因而 `C:/Windows/Temp/../../Users/Public` 这类相对段也能生效。
3. **没有认证/授权层**：该端口上的 `/api/WebFiles/*`、`/api/WebOrderFiles/*` 全部接口匿名可用（cookie 与匿名响应逐字节一致），认证只存在于外层网站，内部 filemover 服务被直接暴露到公网 24006。
4. **目录 ACL 过宽**：服务进程对 `C:/Windows/Temp`、`C:/ProgramData`、`C:/Users/Public` 均有写权限（并能在 ProgramData 下建目录），说明服务账号权限过大。
5. **仅靠扩展名白名单防御**：`.txt/.png/.pdf` 不做内容校验，`.jpg` 仅做魔数检查；白名单是唯一屏障，且是"字符串取最后一段后缀"，多扩展名（`x.jpg.html`）依赖该逻辑才未绕过——防御单点、脆弱。
6. **错误信息不统一**：`"上传的文件路径不合法"` 与 `"对路径“...”的访问被拒绝"` 的差异暴露目录是否存在，进一步降低攻击成本。

## 修复建议

**立即（止血）**

1. **关闭公网直连**：`filemover.sd2000.com:24006` 不应直接对互联网提供 API。在 tengine/网关层将 `/api/WebOrderFiles/*`、`/api/WebFiles/*` 全部置于统一认证与签名校验之后（校验 JWT `ow` 的签名、有效期与 `CustomerId`/`CustomerUser` 归属），并只允许内网回源（`piscenter-filemover:20006` 仅对可信网段开放）。
2. **接口级授权**：上传/列举/删除/改名接口必须校验请求方对 `orderSN`/`CustomerId` 的归属，禁止仅凭参数操作他人订单文件；为每个接口增加"未认证返回 401、越权返回 403"的自动化回归用例。

**根因修复**

3. **废弃 `sourceFilePath` 直接落盘**：只接受服务端可枚举的目标标识（如 `targetType=orderComment|3D|temp`），由服务端在常量根目录下拼路径；如业务确需多目录，用白名单映射（ID → 绝对路径），绝不接受原始路径字符串。
4. **强制路径规范化 + 根前缀校验**：
   ```csharp
   var root = Path.GetFullPath(@"C:\pisweb\upload");           // 固定根
   var target = Path.GetFullPath(Path.Combine(root, serverDir)); // serverDir 来自白名单
   if (!target.StartsWith(root + Path.DirectorySeparatorChar, StringComparison.OrdinalIgnoreCase))
       throw new SecurityException("illegal path");
   ```
   同时拒绝 UNC、盘符切换、`..` 段、ADS（`:`）、结尾点/空格、8.3 短名等变体。
5. **服务端生成文件名**：忽略客户端 `filename`，使用服务端 GUID + 由内容检测决定的扩展名；解析并重编码图片（ImageSharp/WIC）以消除伪造内容。
6. **收敛服务账号权限**：以低权限专用账号运行应用，ACL 上移除对 `C:\Windows\Temp`、`C:\ProgramData`、`C:\Users\Public` 的写权限（这三处本就是任意写的高危落点）；存储根 `C:\pisweb` 与站点目录 `C:\inetpub\wwwroot`、系统目录彻底隔离，且存储根上禁止脚本执行（IIS 中对静态文件目录关闭 handler 映射）。
7. **统一错误响应**：所有路径类失败一律返回同一句 `上传失败` + 内部日志记录，取消"对路径…的访问被拒绝"这类差异化回显，消除路径存在性预言机。
8. **上传侧加固**：限制单文件大小/频率、限制并发、对同 IP 连续 `"路径不合法"` 失败与异常目录目标做告警；对 `C:/Windows/Temp`、`C:/ProgramData` 等非业务目录的上传直接拒绝（业务上根本不需要，属最小化白名单）。

**排查与验证**

9. **事后排查**：审计 `C:\Windows\Temp`、`C:\ProgramData`、`C:\Users\Public`、`C:\pisweb`（含根目录与 `upload\` 各层）在近期新增的 `.txt/.png/.pdf` 文件，核对是否为本业务产生；同时排查日志中 `GetFileInfosV2` 的非业务路径枚举记录，以及 Upload 接口返回 `"上传的文件路径不合法"` 的异常高频来源。
10. **修复验证标准**：匿名请求返回 401/403；携带 `sourceFilePath=C:/Windows/Temp` 的请求返回统一失败且磁盘无新增文件；`GetFileInfosV2` 仅能列举当前客户订单目录；对 `C:/`、`C:/Windows` 等的列举请求被统一拒绝。

## 概述

`https://filemover.sd2000.com:24006` 的 `POST /api/WebFiles/Upload` 与 `POST /api/WebFiles/Upload3D` **完全未鉴权**（不带任何 Cookie 即成功返回落盘路径），且把客户端字段 `tag` / `orderSN` / `TempSerialSN` **直接字符串拼接进存储路径**。攻击者用 `../`、`..\` 即可把上传文件写出预期的 `/upload/<tag>/<date>/` 目录，实测写入 `C:/pisweb/20261031/`、`C:/pisweb/`（存储根）、`C:/pisweb/upload/`。该 `C:/pisweb` 正是 `https://files.sd2000.com:9600/pisweb` 的静态根，写入的文件可被**匿名 HTTP 取回**，实测响应体 md5 与本地文件完全一致。

## 影响与危害

**严重等级：高（High）**

- **未授权写入 + 公开可读**：无需任何账号，即可向 sd2000 对外提供图片/媒体服务的可信域名投递攻击者控制的内容；文件被匿名取回。是一条可用的"可信域匿名文件托管"通道，可用于钓鱼/恶意载荷分发、内容伪造。
- **目录隔离失效**：落点目录完全由请求参数决定，可把文件写进**他人订单号目录**（如 `/pisweb/upload/comment/<别人的orderSN>/`）以及存储根、业务日期目录。订单号与 CustomerId 在该系统接口与前端 JS 中可直接获得，目录本身又可用同主机 `GetFileInfosV2` 匿名枚举（见关联漏洞 #38），因此写入目标可被稳定定位。
- **污染共享静态命名空间**：`C:/pisweb/20261031/`、`C:/pisweb/` 这类目录同时承载正常业务上传产物（实测该根下已有 `zzprobe47.jpg` 等业务文件），攻击者可在其中堆放任意文件、创造大量目录。
- **资源滥用**：无限量上传到公开可达存储，可造成存储/带宽消耗。
- **未升级为 RCE 的原因（边界已实测）**：多级 `..` 最终被夹紧在存储根 `C:/pisweb`，无法越出到 `C:/Windows`、`C:/inetpub/wwwroot`（files 主机 `/20261031/xxx` 返回 404 佐证）；后缀白名单拒绝 `.aspx/.ashx/.asmx/.config/.html/.htm/.svg/.jsp/.php/.exe` 等；文件名固定为服务端生成的 32 位 hex GUID（`filename` 参数被丢弃），无法定向覆盖既有文件。

## 根因分析

1. **鉴权缺失**：`WebFiles` / `WebOrderFiles` 两组控制器（后端 `piscenter-filemover:20006`）没有任何认证/授权过滤器；同一主机 10 个接口的匿名请求与带登录 Cookie 请求响应逐字节相同，说明鉴权与租户归属校验在服务端整体不存在。
2. **路径由字符串拼接构造且未做规范化校验**：落盘路径形如 `root + "/upload/" + tag + "/" + yyyyMMdd + "/" + orderSN + "/" + guid + ext`（`orderSN` 参与时），`tag`/`orderSN`/`TempSerialSN` 未做白名单或字符过滤，`..` 直接交给文件系统解析，`Path.GetFullPath` 归一化后仍被用于写文件，缺少"归一化结果必须位于预期子目录内"的校验。
3. **存储根与公开静态站点同源**：`C:/pisweb` 既是上传落盘根，又被 `files.sd2000.com:9600/pisweb` 以静态文件方式直接暴露（`access-control-allow-origin: *`），上传成功即等于"发布成功"，路径穿越因此具备直接的外部可利用性。
4. **校验层次错位**：只有后缀白名单（且只对部分接口生效），无内容魔数/图像解码校验（伪造 mp4 内嵌 `<script>` 原样落盘）；文件名虽然被强制改为 GUID（这一点客观上阻止了定向覆盖），但**目录仍完全由客户端控制**。

## 修复建议

1. **先补鉴权（最高优先）**：为 `WebFiles/*`、`WebOrderFiles/*` 全部 action 加统一认证中间件（校验 `sl-session`/JWT `ow` 的签名与有效期），租户身份只能从令牌取，绝不接受请求体里的 `CustomerId`/`orderSN` 作为归属依据。
2. **禁止客户端参与路径构造**：`tag` 改为服务端枚举白名单（如 `comment|customer|yunxiu|3D`），`orderSN` 用 `Guid.TryParse` 强校验，`TempSerialSN` 限制为 `^[A-Za-z0-9_-]{1,64}$`；落盘路径用 `Path.Combine` + `Path.GetFullPath`，随后断言
   `fullPath.StartsWith(Path.GetFullPath(rootWithTrailingSeparator), StringComparison.OrdinalIgnoreCase)`，不满足直接 400；同时封装统一的 `SafeJoin` 工具函数供所有上传点复用。
3. **上传与公开服务解耦**：上传落盘目录移出静态根（如 `D:/data/uploads`），对外只通过带鉴权与租户校验的下载/预览接口输出（`Content-Disposition: attachment` 或经签名 URL 短时授权），关闭目录列举与默认索引。
4. **内容与类型双重校验**：后缀白名单 + 服务端解码校验（`System.Drawing`/ImageSharp 重新编码图片、PDF/MP4 校验魔数与结构），拒绝"扩展名合法但内容任意"的文件；禁止在用户内容域返回 `text/html`，补充 `X-Content-Type-Options: nosniff`、CSP，收紧 `Access-Control-Allow-Origin: *`。
5. **运行侧加固**：为上传接口加限速/配额/审计（记录来源 IP、目标路径、大小、md5），对 multipart 字段中出现 `..`、`/`、`\` 的请求在 WAF 层直接拦截；多实例后端统一修复并回归"匿名上传必须 401"。
6. **历史排查**：检索 `C:/pisweb` 下异常目录（如根级 `2026xxxx`、`upload/comment/` 下的陌生目录）与近 30 天上传日志，确认是否已有被投递的恶意内容；对 `files.sd2000.com` 做内容巡检。

## 影响与危害

1. **服务器文件系统全量暴露（核心危害）**：攻击者不需要账号，即可枚举 `C:\` 及所有可读子目录的文件名与扩展名。实测一次请求返回 3877 条 System32 文件（458 KB），完整还原了主机类型（Windows Server + IIS）、组件清单与目录结构。
2. **为后续攻击提供精确打击面**：已知 `C:\inetpub\wwwroot` 存在（`iisstart.htm`/`iisstart.png`）、`C:\Windows\System32\drivers\etc` 存在（`hosts`、`lmhosts.sam`、`networks`、`protocol`、`services`）、`C:\Windows\System32\inetsrv` 存在（`appcmd.exe`、`Microsoft.Web.Administration.dll`、各 `auth*.dll` 认证模块，共 77 项）、`C:\Windows\System32\winevt\Logs` 存在（297 个 `.evtx` 日志）。这些信息可直接用于选择提权/横向/日志篡改路径。
3. **绝对路径与权限信息泄露**：越权目录会返回原始 .NET 异常，例如 `对路径“c:\Windows\System32\inetsrv\config”的访问被拒绝。` 直接暴露了服务器本机绝对路径、盘符与进程账户的访问控制边界（`config`、`C:\Windows\System32\config` 均被拒绝，说明服务账户权限有限但不隔离目录枚举）。
4. **资产测绘成本极低**：响应无速率限制、无认证、无验证码，可脚本化批量子目录扫描，把内网主机的文件清单批量拉走。
5. **与同域其他缺陷叠加**：同一组接口（`/api/WebFiles/Remove`、`/api/WebOrderFiles/BatchRemove`、`/api/WebFiles/Upload`、`/api/WebFiles/Upload3D` 等）经对比测试**带 cookie 与完全匿名请求返回完全一致**，即整条文件服务控制器族缺少鉴权（详见"关联风险"）。目录枚举结果为这些未鉴权写/删操作提供了准确的目标路径，二者叠加的实际风险高于单个信息泄露。

**定级理由（High）**：漏洞本身是"未授权 + 任意路径"的目录枚举，不直接读出文件内容（未找到可下载文件正文的端点，见"边界与未验证"），因此未定为 Critical；但其无需认证即可完整测绘生产服务器文件系统、泄露本机绝对路径与权限边界，且为同主机一批未鉴权写/删操作提供了精确落点，故定为 **High**。

## PoC

以下脚本可一键导出服务器任意可读目录清单（无需任何凭据）：

```python
#!/usr/bin/env python3
# 用法: python3 enum_dirs.py "/"            # 列盘符根
#       python3 enum_dirs.py "C:/Windows"  # 列任意目录
import sys, json, urllib.parse, urllib.request, urllib.error, ssl

BASE = "https://filemover.sd2000.com:24006/api/WebOrderFiles/GetFileInfosV2"
ctx = ssl.create_default_context(); ctx.check_hostname = False; ctx.verify_mode = ssl.CERT_NONE

def ls(path):
    url = BASE + "?pathEncrypt=" + urllib.parse.quote(path, safe="")
    req = urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0"})  # 无 Cookie
    try:
        body = urllib.request.urlopen(req, timeout=20, context=ctx).read()
    except urllib.error.HTTPError as e:
        body = e.read()          # 500 = 存在但拒绝访问，并泄露绝对路径
    d = json.loads(body)
    if d.get("Result") is None:
        print(f"[DENIED/ERROR] {path} -> {(d.get('Error') or {}).get('Message')}")
        return []
    return [x["Name"] + (x["Extension"] or "") for x in d["Result"]]

if __name__ == "__main__":
    root = sys.argv[1] if len(sys.argv) > 1 else "C:/Windows"
    names = ls(root)
    print(f"# {root}: {len(names)} entries")
    for n in names:
        print(n)
```

## 根因分析

1. **接口缺少鉴权**：`WebOrderFilesController.GetFileInfosV2` 未加 `[Authorize]`（或全局过滤器未覆盖该控制器）。证据是带完整 cookie、伪造 cookie、完全匿名三种状态返回码与结果结构完全一致，且响应体里 `UnAuthorizedRequest` 恒为 `false`——说明认证中间件根本没参与该请求。
2. **路径参数未做任何校验/规范化**：`pathEncrypt` 名为"加密路径"，实际被直接当作明文目录路径传给文件枚举逻辑：
   - 未强制为"存储根目录（如 upload/customer）下的相对路径"；
   - 未做 `Path.GetFullPath()` + 根目录前缀校验，导致 `../`、`..\..\`、绝对盘符路径全部可用；
   - 未做符号/多重分隔符规范化（`C:\\Windows`、`C:/`、`/` 都能命中）。
3. **异常直接透出**：枚举逻辑把 `Directory.GetFiles` 抛出的 `UnauthorizedAccessException` 原样包装进响应 `Error.Message`，泄露本机绝对路径与进程账户 ACL 边界；前端错误结构与业务错误结构共用，导致这个"内部实现细节"对外可见。
4. **同一控制器族整体缺鉴权（旁证）**：`/api/WebFiles/Remove`、`/api/WebOrderFiles/BatchRemove`、`/api/WebFiles/Upload`、`/api/WebFiles/Upload3D`、`/api/WebOrderFiles/RenameFolder` 等 10 个端点，带 cookie 与匿名的状态码/响应长度**逐条一致**（例如 `Remove` 两者都是 `200/4` 返回 `true`，`BatchRemove` 都是 `200/88` 返回 `Success:true`）。这说明鉴权缺失不是单点疏漏，而是该文件服务的控制器层没有统一认证。

## 修复建议

**立即（P0）**

1. **给文件服务控制器补鉴权**：`WebOrderFilesController` / `WebFilesController` 全部 action 加 `[Authorize]`，并在启动时注册全局 `AuthorizeFilter`，用白名单方式排除确实需要匿名的方法（如健康检查），避免再漏。校验"匿名 / 伪造 cookie / 真实 cookie"三种请求的响应必须不同（未登录应 401/403）。
2. **路径白名单收敛**：把 `pathEncrypt` 语义改为"受限相对路径"，服务端落盘前统一：

```csharp
var root = Path.GetFullPath(Configuration["FileStorage:Root"]);      // 例如 D:\FileStore
var target = Path.GetFullPath(Path.Combine(root, relPath));
if (!target.StartsWith(root + Path.DirectorySeparatorChar, StringComparison.OrdinalIgnoreCase))
    throw new BadHttpRequestException("invalid path", 400);
```
   同时拒绝绝对路径（`Path.IsPathRooted`）、UNC（`\\`）、包含 `..` 的段，以及多重分隔符。
3. **停止透出内部异常**：`UnauthorizedAccessException`、`DirectoryNotFoundException` 一律返回统一 404/403，不返回 `c:\...` 绝对路径；生产环境关闭详细错误回显。
4. **不要用"加密"掩盖鉴权缺失**：`pathEncrypt` 若要保留，必须真正做服务端签名/加密（如 AES-GCM + HMAC，密钥仅服务端持有），且解密后仍执行第 2 步的白名单校验——加密不能替代授权。

**短期（P1）**

5. 对本服务做速率限制与异常审计告警（同 IP 短时间内大量不同 `pathEncrypt` 值、或非业务目录命中的，直接阻断并记录）。
6. **对上传/删除/改名等写操作同步复核并修复**（见"关联风险"）：这些接口同样匿名可用，且 `Upload` 返回的 `FilePath` 已证实为真实落盘路径（`/upload/comment/20261031/<32hex>.png`），与目录枚举组合后可以精确定位文件。建议一并按"认证 + 路径白名单 + 归属校验（fileId/orderSN 必须属于当前客户）"整改。
7. 降低进程账户权限：`piscenter-filemover` 服务账户不应有对 `C:\`、`C:\Windows` 的读权限（除必要部分），用最小权限原则重建 ACL；文件存储根目录独立盘符/独立账户。

**长期**

8. 在 CI 中加入接口鉴权矩阵回归测试（对每个 API 断言"匿名请求必须 401/403"），并把 `GetFileInfosV2` 这类"参数即路径"的接口纳入 SAST 规则（`Directory.GetFiles`/`File.Open` 的参数若来自请求参数即告警）。
9. 隐藏上游服务名等内部信息（`piscenter-filemover:20006` 不应出现在对外错误体）。

## 关联风险（同主机实测观察到，未纳入本漏洞定级）

这些是同一服务在验证过程中被顺带确认的匿名可用行为，**未做破坏性利用**，仅供修复排期参考：

- 认证矩阵（POST `{}`，带 cookie / 匿名 响应完全一致）：`/api/WebFiles/Remove` `200/4`、`/api/WebFiles/Upload` `200/2`、`/api/WebFiles/Upload3D` `200/161`、`/api/WebFiles/UploadFile` `200/2`、`/api/WebOrderFiles/Upload` `500/230`、`/api/WebOrderFiles/BatchRemove` `200/88`、`/api/WebOrderFiles/RenameFolder` `200/134`、`/api/WebOrderFiles/CopyAIRetouchingFiles` `500/162`、`/api/WebOrderFiles/DownloadRemoteFiles` `500/159`、`/api/WebOrderFiles/BatchCreateOrderFileMerge` `200/89`。
- `POST /api/WebFiles/Upload`（multipart，匿名）返回真实落盘路径 `/upload/comment/20261031/<32hex>.png`；带 `orderSN` 时返回 `/customer/comment/20261031/<orderSN>/<32hex>.png`。
- `POST /api/WebFiles/Upload3D` 传入 `TempSerialSN=../../Windows/Temp` 时，响应 `FilePath` 回显 `/upload/3D/20261031/../../Windows/Temp/SK.png`（**路径穿越被回显但未证实文件真实落到该位置**：随后重新枚举 `C:\Windows\Temp` 未见该文件；同样地，`/upload/comment/...` 上传后自查目录为空）。即"写入穿越"未证实，仅"回显穿越"已证实。

**严重等级：medium**（若下述路径注入被证实可写出 `/upload` 之外，应升级为 high/critical）

## 根因分析

1. **认证层缺失（主因）**：`24006` 的 tengine 直接把内网 ASP.NET Web API（`piscenter-filemover:20006`）暴露到互联网，Web API 侧未启用任何认证中间件，控制器与动作上无 `[Authorize]`，也没有 CSRF 校验。因此 `sl-session` / `ow` JWT 对服务端完全不生效（`UnAuthorizedRequest` 恒为 false，匿名与登录态响应逐字节相同）。这已超出"配置疏漏"，属于**整段服务无鉴权设计**。
2. **路径参数未规范化**：`Upload3D` 用字符串拼接方式构造 `{根}/3D/{日期}/{TempSerialSN}/{随机名}.{ext}`，未对 `TempSerialSN` 做白名单校验，也未在拼接后执行 `Path.GetFullPath` 并校验结果仍位于允许根目录之下；返回体直接把未规范化路径回显，说明校验环节整体缺失。
3. **文件校验只做后缀、不做内容**：仅按扩展名白名单放行 pdf/jpg/png，未做魔数校验/图片解码/重编码，导致任意内容可以合法扩展名落盘；同时上传目录与 Web 站点未做隔离与 `Content-Type`/`Content-Disposition` 控制。
4. **文件操作接口以"路径字符串"为唯一标识**：`Remove` / `BatchRemove` / `RenameFolder` 接受调用方给的绝对路径，既不从令牌推导客户归属，也不校验路径是否属于该客户；且对不存在的路径直接返回 `Success:true`，属错误吞掉，掩盖了越权/越界行为。
5. **内部错误外泄**：未启用自定义错误页，未匹配路由返回内网回源地址 `piscenter-filemover:20006`，`pathEncrypt` 拒绝时报出服务器绝对路径（`c:\Windows\System32\inetsrv\config`）；同时暴露 `X-AspNet-Version` / `X-Powered-By`。

## 修复建议

**优先级 P0（立即）**

1. **给 24006 补齐认证边界**：在 tengine / API 网关层对该端口强制鉴权（校验 `ow` JWT 签名 + `sl-session`，未通过返回 401/403），并在 ASP.NET 侧为 `WebFilesController` / `WebOrderFilesController` 全局加 `[Authorize]`，禁止匿名访问；同时校验 `Origin`/`Referer` 或加 CSRF Token，防止已登录用户被跨站利用。
2. **`TempSerialSN` 严格白名单化**：仅允许 `^[A-Za-z0-9_-]{1,64}$`，拒绝 `/`、`\`、`..`、绝对路径、控制字符与 URL 编码变体（注意需先解码再校验）；拼接后必须 `var full = Path.GetFullPath(Path.Combine(root, serial));` 且断言 `full.StartsWith(root + Path.DirectorySeparatorChar)`，否则直接拒绝。返回给客户端的路径改用自行构造的规范路径，不要回显入参。
3. **上传落盘与业务归属绑定**：`TempSerialSN` 不应由客户端任意指定，改由服务端根据令牌中的 `CustomerId` / 订单号生成；上传目录应与 Web 根目录分离（建议独立文件服务器/NAS），目录上移除脚本执行权限，禁止 IIS 对 `upload` 目录解析 `.asp/.aspx/.config`。
4. **文件操作接口重构**：`Remove` / `BatchRemove` / `RenameFolder` 改为以"服务端签发的 fileId"为标识，服务端据 `CustomerId` 反查真实路径并校验归属；对不存在的目标返回明确错误（404/409），不得返回 `Success:true`；所有路径参数统一走上述规范化校验，禁止 `/`、`..`、盘符。

**优先级 P1（短期）**

5. **内容校验与安全下发**：校验魔数并解码/重编码图片、PDF 解析后再落盘；服务端生成随机文件名并保留原始扩展名映射；静态下发时强制 `Content-Type` 与 `Content-Disposition: attachment`，并加 `X-Content-Type-Options: nosniff`；若必须经 `content.sd2000.com` 分发，确认该 CDN **不**服务用户上传目录，或对其加签名 URL 与独立域名隔离。
6. **配额与监控**：按来源 IP / 会话做上传速率与总容量限制，监控异常上传量、文件名模式与 `../` 出现；对 `FilePath` 中出现 `../` 的请求直接告警。

**优先级 P2（长期）**

7. **关闭信息泄露**：启用 `customErrors` / 统一异常响应，去掉内网回源地址 `piscenter-filemover:20006` 与绝对路径回显；移除 `X-AspNet-Version`、`X-Powered-By` 响应头；关闭 `OPTIONS` 上的无效 CORS 配置（当前 `Access-Control-Allow-Origin: 0` 与 `Allow-Credentials: true` 属错误配置）。
8. **统一鉴权体系**：把 `www` 侧（`sl-session` + `ow` JWT）与文件服务打通为同一套身份校验，避免"业务站点要登录、文件服务完全裸奔"的割裂架构；对 `filemover`、`files.sd2000.com:9600`、`fm.sd2000.com:22443` 等文件类端口做一次统一的暴露面梳理与加固。

## 待确认 / 未验证项

- `TempSerialSN` 注入的 `../` 目前只证实"出现在返回路径中"；**是否真正写出 `/upload/3D` 之外**未能验证（本端口不提供静态回读，`/upload/*` 全 404；`GetFileInfosV2` 也列不到该目录，见 finding#7 附注）。建议在授权窗口内用无害标记文件定位落盘位置后再定级。
- `Remove` / `BatchRemove` / `RenameFolder` 对**真实存在**的业务文件是否真会删除/改名未验证（对不存在路径也返回成功，返回值不可作为生效证据）。若证实生效且可跨客户操作，应升级为 high。
- `content.sd2000.com/upload/...` 是否对外提供用户上传内容未验证（前端 bundle 中存在 `/upload/ → https://content.sd2000.com/upload/` 的替换逻辑）。
- 上传体积上限、是否落盘到本机还是独立文件服务器未确认。
